## 目标与依据

请将已确认的设计落实为**最简可运行版本**：模型在同一工具循环中自主读取空间资料、观察、构建和修订局部空间记忆、维护判断、计算和移动，并留下真实交互记录。接手后按下述范围实现和验证，保持架构简洁。

当前规范以 [Architecture.md](../../Architecture.md) 和 [SpatialMemory.md](../../SpatialMemory.md) 为准；任务形式见 [Tasks.md](../../Tasks.md)，评分口径见 [Experiments.md](../../Experiments.md#protocol)。旧消息只用于追溯，不逐条作为额外需求执行。

## 重构位置与旧实现的参考范围

**这是一次完整重构，新的 Harness 在 `src/harness-pi/` 中独立组织和实现。** 当前设计与原 `src/harness/` 差距较大，应按现行设计建立基于 Pi 的运行结构，不复制旧目录后逐文件修补，也不以保留旧类、接口或调度方式为目标。

`src/harness/` 可用于了解现有环境交互、场景数据格式、任务协议和已遇到的问题；符合新设计的独立功能可以选择性复用。Agent 循环、工具组织、空间记忆与上下文管理以现行设计和 Pi 的能力为依据，不照搬旧实现。现有场景数据、任务素材和环境能力继续按需使用。

“完整重构”要求新版本形成独立、完整的运行闭环；实现保持最简，优先复用 Pi，不重新实现通用 Coding Agent。旧 `src/harness/` 本轮保留作参考，重构不附带删除旧代码或覆盖历史实验。

## 开发基座：先复用成熟 Coding Agent

用户新增要求：尽量与主流 Coding Agent 保持一致，充分保留模型原有的 Agent／Coding 能力。**本轮推荐以 Pi 的完整 `pi-coding-agent` SDK 为基座，增加导航扩展；Habitat 仍由 Python 运行。** 先验证指定模型服务与基座的兼容性，再接入导航。固定经过核验的发布版本和对应文档，当前官方包名为 `@earendil-works/pi-coding-agent`。

- 复用基座会话、文件／命令工具、模型适配、扩展和压缩。不要只取 `pi-agent-core` 后重新实现这些功能，也不要求为全 Python 而重写基座。
- 原生 `read`、`write`、`edit`、`bash` 满足通用操作；导航扩展负责看图增强、绘图、观察、移动与完成提交。原先“九工具、仅 Python、edit 唯一写入口”不再是硬约束，以公开读写边界和完整变化记录约束行为。
- Coding 环境内提供 Python，允许模型写脚本、执行、检查输出和修改重跑。命令只能访问任务公开工作空间；仅设置 `cwd` 不构成隔离。服务密钥、模拟器内部和评分数据留在环境之外。
- **压缩方案暂未定稿。** 本轮沿用 Pi 原有机制，仅通过现有扩展做[导航摘要提示词的简单适配](../../Architecture.md#compaction-prompt)，先验证一次基本续接。多模态信息如何压缩、哪些证据应保留及其效果，后续再仔细研究；不将当前提示词当作最终解答，也不为本轮另写压缩引擎。记录实际输入和已知限制，基座 session 文件不能直接替代完整实验记录。
- Codex App Server／SDK 是原样复用 Codex 的备选，需先满足自定义服务的 Responses 协议要求。本轮不同时建设两个运行基座，也不预设 Pi 与 Codex 性能相同。

选型理由、官方链接与工具映射见 [开发基座](../../Architecture.md#framework)。

### 安装、运行与通信

**采用 SDK 直接嵌入。** NavCraft 的 TypeScript 入口导入 Pi，二者运行在本机同一个 Node 进程内，通过函数与事件交互，不需要另起 Pi 网络服务。模型推理由 Pi 的 provider 调用指定远程 API。

导航工具连接一个常驻 Python／Habitat 进程；首版使用子进程 stdin/stdout 的 JSONL 请求与响应即可，日志走 stderr。一次动作后返回公开反馈与图片引用，由导航扩展读取并作为图像内容交给模型；不每走一步重启模拟器。这是 NavCraft 与环境的通信，不是 Pi 的 CLI RPC。

| 内容 | 放置与运行方式 |
|---|---|
| NavCraft 新 Harness 与扩展 | `src/harness-pi/`，保持源码目录简洁 |
| 本地维护的 Pi 核心源码 | `src/harness-pi/pi/`，保留所需上游包的完整边界、许可证与版本来源；不复制整个 Pi monorepo |
| 外部依赖与安装配置 | 由仓库根目录的 `package.json`、`package-lock.json` 与 npm workspaces 统一管理，以根目录 `node_modules/` 为安装位置；不在各源码包中单独安装依赖 |
| 模型工作空间与运行产物 | 每次运行放在 `runs/<run-id>/.../workspace/` 等独立目录，Pi 的任务工作目录指向这里，不指向 Harness 源码 |

推荐目录如下；这是待实施布局，不表示这些包已安装：

```text
NavCraft/
├── package.json                 # 项目依赖与本地 workspaces 声明
├── package-lock.json            # 锁定依赖版本
├── node_modules/                # 普通依赖与指向本地包的链接
└── src/harness-pi/
    ├── ...                     # NavCraft 入口与导航扩展
    └── pi/
        └── coding-agent/       # 需要修改的 Pi 包，含自身 package.json
```

源码、包配置、lockfile 和上游许可证纳入版本控制。`.gitignore` 的 `node_modules/` 规则覆盖仓库根及任意子目录的安装依赖；不提交其中的包或链接。

用户所需的是**本地可查看、可修改的 Pi 核心源码，依赖留在源码目录外**。继续复用完整 Coding Agent 的会话、工具与压缩能力，不因源码放置方式而改成只用底层循环。按实际需维护的包选择源码范围，其余包使用固定版本依赖；运行入口必须引用这份本地源码或其构建结果，不能本地只存一份参考代码、实际却运行另一份 npm 版本。不要直接修改安装目录里的依赖。

**本地源码采用 workspace 链接，效果类似 Python 的可编辑安装。** 在根 `package.json` 中将需要修改的 Pi 包声明为 workspaces，根目录执行 `npm install` 时自动建立指向本地包的软链接；不修改的 Pi 包和第三方库按普通依赖安装。保留包名并核对版本范围与实际解析路径，确保使用本地修改版。[npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/)

- npm 的默认安装位置就是项目 `node_modules/`；全局 `npm install -g` 主要用于命令行程序，不作为本项目 SDK 依赖的安装方式。`npm link` 也支持可编辑链接，但本项目同仓库开发使用 workspaces 即可。
- 链接指向整个包；Pi v1.2.0 的 SDK 入口为 `dist/index.js`，因此修改 TypeScript 后仍需 build，开发时可使用 watch 自动编译，并重启运行进程。只改源码通常无需重新安装，依赖声明变化时才需重新安装；保留构建所需的配置与资源。
- 安装后检查依赖实际布局。npm 遇到版本冲突可能生成嵌套 `node_modules/`，workspaces 本身不保证绝无嵌套；优先对齐兼容版本以满足依赖留在 Harness 源码目录外的要求，不手工搬动包或强制覆盖不兼容版本。

## 实现范围

1. **一个模型与工具循环。** 在 `src/harness-pi/` 中使用 Pi 的现成循环建立新 Harness；任务提供目标、允许资料、工具及结束规则，模型决定调用顺序。按需复用环境和资产读取能力，避免继承旧 Harness 的整体结构。
2. **三种关联的空间记忆与局部在线构图。** 地图、实体文本和证据图片通过稳定 ID 与图片引用关联。`scene/` 中的基础墙层与初始资料只读，墙层不带旧物体图元或标签；`memory/maps/<map>.entities.json` 是唯一当前非墙图元，`memory/entities/<ID>.md` 是唯一当前实体卡片。初始化只复制任务允许的预建实体／卡片，也可从空记忆开始。模型可在线建立新 ID、修正位置、连接和证据；未知几何可为 `null`。删除后不得从 `scene/` 回退恢复。`render_map` 读取墙层、当前图元和状态，不自动定位；字段及一致性规则见 [SpatialMemory](../../SpatialMemory.md)。
3. **原生 Coding 工具＋必要导航扩展。** 通过 `write`／`edit`／`bash` 更新记忆，不另设实体增删改工具；增加可经 `bash` 调用的轻量记忆检查入口，与 `render_map` 共用格式规则。`view_images`、`render_map`、`nav_observe`、`nav_step`、`nav_finish` 提供导航能力，在已有观察／动作工具中补充所需视角与动作参数，具体接口见 [工具设计](../../Architecture.md#tool-design)。脚本和临时产物放入 `scratch/`，持续判断保存到 `memory/`。涉及同一环境状态的导航调用按顺序执行；不要求模型每步写记忆或每条任务用遍工具。
4. **增量上下文与基本压缩续接。** 配置并复用 Pi 会话／压缩，正常轮次追加实际消息与图片，不按固定轮次滚动删图。先做导航摘要的临时适配，检查关键引用与近期工具调用配对，保证压缩后能继续执行；缓存指标按服务实际返回记录。更完整的压缩策略留待后续研究。
5. **可核查的运行产物。** 保存实际模型输入输出、工具调用与反馈、图片、记忆修改和最终结果。公开观察与模型记忆放入工作空间，私有评分和完整审计记录分开保存。

待实现范围是**使用预构建记忆、维护运行判断，以及最简局部在线构图和导航辅助能力**。基础墙层保持只读；本次设计更新不增加长程构图任务或新 benchmark。训练、额外模型协作与大规模评测留待后续。

用户指定服务为 `http://221-api.undertides.cn`，模型名为 **`gpt6.1sol`**。密钥已单独保存于仓库根目录 `.env.harness-test`，权限为 `0600`，受现有 `.gitignore` 排除。配置项是：

按以下顺序做小规模验证，预算在运行前明确并记录：

**测试默认使用已建好的地图。** 除第 4 项记忆构建专项外，直接从 `data/scene_maps` 加载任务允许的地图、实体描述和证据，初始化当前记忆；不让模型重新构建，不把构图成功作为导航、工具或压缩等功能测试的前提。运行中的定位估计、计划和记忆更新仍按设计进行。

1. **Coding 基座与资料。** 先让指定模型实际完成“读资料→写／执行 Python 脚本→看结果→继续调用工具”，验证多图、工具续接和推理配置。再检查地图／图片引用、记忆修改与公开资料边界；本步骤成功不能代替导航效果验证。
2. **局部闭环。** 从现有原子素材选一条查询 QA 和一条局部 IA，重新运行模型；IA 必须实际观察、运动并核验事件，不能用文字宣称完成。优先选 Qa 场景中已知可达的短任务。
3. **三类导航接入。** ObjectNav、指令导航各选一条 Qa 开发任务。GOAT 可取第一条链的前两个连续目标形成单独的 smoke 输入，以验证目标切换和记忆保留；保留原 manifest，并明确这只是截短功能测试。
4. **记忆构建局部专项。** 单独准备一个房间或相邻局部区域的测试副本，仅提供墙图或部分实体，基于真实观察完成一次“建立新实体／卡片→检查并重绘→取得新视角并修订→后续查询或行动使用”。不修改归档地图，不要求全场景重建、长程探索或每步写入，也不另建 benchmark。分别记录文件、引用和重绘是否正常，以及实体身份、位置、连接和证据是否符合真实空间；格式检查通过不等于空间判断正确，空间正确性由模型不可读的核验资料或实际执行另行核验。
5. **基本压缩续接。** 用真实交互在单独测试中降低预算触发一次压缩，再继续调用工具；检查任务、观察引用及调用配对，记录待核实判断、旧位置或视觉证据是否丢失／失真。该测试单独标注预算，只验证临时方案能否续接，不代表压缩策略已经充分验证。

验收重点是**真实闭环可运行、边界正确、记录完整**。工具错误与模型导航失败分开记录；完整导航如实报告结果，不把本轮少量测试解释为成功率评测。发现运行问题后修复并定向复测，避免反复无目的跑整套任务。
