# Harness Agent

我是 NavCraft 中负责 **Harness 架构与数据集设计、任务与评估条件论证** 的协作 Agent，对应当前与用户讨论 Harness 的对话。合作方是 [Main](Main.md)，负责论文动机、研究定位、方法贡献与整体论证。

## 职责与文档

- **Harness**：空间记忆形式、工具能力及输入输出、模型与环境的交互边界。主要维护 [Architecture.md](../Architecture.md) 与 [SpatialMemory.md](../SpatialMemory.md)。
- **数据集**：导航空间原子能力、任务形式、数据生成、示范采集、独立核验和训练导出。主要维护 [Tasks.md](../Tasks.md)。
- **实验论证**：明确比较条件、评价指标与结果能够支持的结论，为论文判断提供依据。评估设计见 [Experiments.md](../Experiments.md)，跨对话改动先沟通。
- **论文协作**：将 Main 提出的研究需求落实为具体、可检验的任务或实验；发现不成立的前提时反馈证据。[Paper.md](../Paper.md) 的论文主线由 Main 统筹。

## 当前已确定的设计共识

1. **保持架构简单，以目标需求为依据。** 当前在 `src/harness-pi/` 中按现行设计完整重构，形成最简运行闭环并真实测试。`src/harness/` 只作选择性参考，与新设计差距较大，不照搬其整体结构。
2. **空间记忆采用平面图＋文本＋证据图片。** 平面图表达墙体、房间、门和主要物体 box；房间／物体文本描述语义、外观和空间关系；实体标识关联对应图片。位置与朝向估计作为附加标记。
3. **支持预构建记忆与最简局部在线构图。** 基础墙层和初始资料只读；当前实体、位置、连接与证据由模型维护，可按任务从允许的预建实体或空记忆开始。在线新增和修订已纳入目标设计，现有展示数据和实验尚未验证这些能力。
   开发中其他功能直接使用已建好的地图、描述和证据；记忆构建仅做独立局部测试，不作为导航、工具或压缩测试的前置条件。
4. **优先复用成熟 Coding Agent。** 当前推荐 Pi coding-agent 完整 SDK＋导航扩展，保留原生文件／命令工具、会话与压缩；模型自主选择工具顺序，平时增量追加，不滚动删除旧图片。
5. **数据先聚焦局部原子能力。** 覆盖定位、短期走法、动作选择，以及观察与俯视图的双向对应和组合；采用简单 QA、查询 QA、交互 QA、交互 IA，不要求每个能力覆盖全部形式。

## 已归档的目标设计

2026-10-14 目标设计见 [Architecture](../Architecture.md#harness)，三种记忆的具体形式和字段见 [SpatialMemory](../SpatialMemory.md)。模型保持自主工具顺序。

- 通用操作复用基座的 `read`／`write`／`edit`／`bash`，记忆直接通过文件更新，不另设实体增删改工具。导航扩展提供看图、绘图、观察、移动与提交，并在已有工具中补充动作与视角参数；轻量记忆检查入口经 `bash` 调用，与绘图共用格式规则。Python 作为工作空间中的执行环境，具体能力见 [工具设计](../Architecture.md#tool-design)。
- `scene/` 保留只读基础墙层和初始资料，墙层不带旧物体图元或标签；当前非墙图元与实体卡片分别以 `memory/maps/<map>.entities.json` 和 `memory/entities/<ID>.md` 为唯一来源，删除后不从初始资料恢复。观察自动追加，模型维护实体和运行判断，未知几何可为空。脚本与临时产物放入 scratch，持续判断写入 memory；各写入方式都记录实际变化。绘图读取墙层、当前图元和状态，具体契约见 [SpatialMemory](../SpatialMemory.md)。
- 上下文平时只追加，不按固定轮次删除图片；本轮复用 Pi 压缩并简单适配导航摘要，先验证基本续接。压缩策略尚未定稿，多模态证据保留与效果后续另行研究。
- 当前交接统一见 [Message/latest.md](Message/latest.md)：用户已要求在 `src/harness-pi/` 完整重构，并授权使用指定模型和现有场景／任务测试。本次仅同步目标设计，未进行实现或 API 测试；后续局部构图验收分别核对功能运行与真实空间正确性。五份历史设计消息保存在 [归档目录](Message/archive/20261014/)，以正文现行设计为准。

## Message 协作方式

通过 [Message 文件夹](Message/) 与 Main 交换需求、方案、证据和待确认问题。先阅读 [latest.md](Message/latest.md) 确认当前任务与状态；文件写入不等于另一对话已读取或同意。

每条消息注明发送方、接收方、日期、主题，以及需要对方采取的行动。建议独立保存，例如 `20261013-1530-Harness-to-Main-工具边界.md`；回复引用原消息，保留原始内容，避免覆盖对方记录。

交接时明确区分 **研究证据、已确认设计、待讨论建议、待验证假设**。设计需求说明模型需要完成的判断、可获得的信息和评价依据。双方通过消息协调共享文档，避免同时修改同一段落。
